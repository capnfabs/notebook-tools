# Bbox accuracy: cap sent images at 3.6 MP, keep effort `high`

On 4 two-page spreads (`spread-wood-3`…`-6`), boxes for images sent at 2576px came back squeezed toward the top-left by ×0.81–0.86. The API shrinks images until both sides are ≤ 2576px *and* they cost ≤ 4,784 visual tokens, one per 28×28px patch, about 3.75 MP ([docs](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates#how-claude-resizes-and-pads-images)), and Claude answers in the shrunk image's pixels. The docs' resize algorithm predicts the scale for all 4 to ±0.01. So 1:1 pixel boxes only hold under both limits, and transcription now sends at most `ocr::MAX_IMAGE_PIXELS` (3.6 MP, slightly under so partial patches still fit). Requests also set `"transformations": {"oversized_image": "error"}`, so if our sizing ever drifts the API rejects the image instead of silently resizing it. At that size, and at 1288px, line boxes follow each handwritten line and uncertain-word boxes land on or next to their word. Boxes tend to sit up to a third of a line low, and one overran the image bottom by 9px. Good enough for the line-level PDF text layer and for tapping uncertain words. No crop/zoom tool, tiling or local detection is needed.

Effort: `low`, `medium` and `high` cost about the same (~5.5k in, 2–4k out, 20–45s), so keep `high`. `xhigh` flags a few more uncertain words for ~3× the output tokens and 50–75s. `max` hit the 16k token cap on every spread. Claude's line index for uncertain words is sometimes off by up to ~15 lines (16 words not found within ±2). Going by which line box holds the word's box was right for every word we could check, so lookup should go by box.
