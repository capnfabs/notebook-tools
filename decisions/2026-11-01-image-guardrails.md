# Guarding against personal content in commits

The repo is going public and its fixtures came from the user's diary, so a pre-commit hook (`.githooks/pre-commit` → `scripts/check-images.sh`) checks every staged image that's added or changed. An image must be listed by git blob id in `scripts/reviewed-images.txt`, which only the user adds to (`--approve`). Renaming keeps the approval; any edit loses it. Its metadata may only say how to show it: colour profiles, rotation (EXIF Orientation), colour space, pixel layout, format versions and iPhone HDR gain maps. Any other EXIF, XMP, IPTC, GPS, maker note, JPEG comment or PNG chunk fails, so unknown text chunks do too. The check uses exiftool. Text isn't scanned: there's no deny-list of names and no secret scanner. Instead, agents ask before committing anything personal (CLAUDE.md). Git never turns on hooks from a clone, so `scripts/check.sh` fails until `core.hooksPath` is `.githooks` (and exiftool is installed) rather than setting it itself. There's no CI copy, since the hook covers the one machine committing. `scripts/test-check-images.sh` tests the script and hook in throwaway repos.

Reason: Human Taste (hook only, the allowlist and metadata check, allowing rotation and colour tags, no deny-list or gitleaks, the CLAUDE.md wording); unquestioned agent recommendation for keying approval on blob ids and failing closed on PNG chunks; Human Taste for check.sh failing rather than enabling the hook.
