# Mac menu bar: one command table, one input frontend

Every menu action is a `Command` (`crates/app/src/command.rs`), defined once with its label and shortcut (the label's text is in the strings file since `2026-10-30-strings-in-fluent.md`). `MENUS` lays out the menu bar. The app decides what each command can do right now (`command_state`: enabled, checked, title) and runs it. Input comes through exactly one `Frontend`: the muda menu bar on macOS, which takes the key equivalents itself, or `EguiKeys` everywhere else, tests included. The two are never on together. A disabled item's key reaches egui as an ordinary key press, so ←, → and ⌘⌫ keep editing text in a transcript line. A shortcut overlay for another platform could be built from the same data. Reason: Human Taste (no "both on" input, a single source of truth). Using muda was the task's suggestion.

Layout: the app menu (Settings… ⌘, since `2026-10-30-settings-dialog.md`), then File (Add Pages… ⇧⌘I, Export ⌘E, which re-exports once there's a last export, and Export… ⇧⌘E), View (the three views at ⌘1–3, Previous/Next Page at ←/→), Page (Transcribe ⌘T, Force ⇧⌘T, Transcribe All ⌥⌘T, Move ⌘←/→, Sort, Delete ⌘⌫) and Window. ⌘N and ⌘O are kept for projects later, so adding photos is "Add Pages…" and not "Open". Reason: Human Taste (Go folded into View, Add Pages naming, keeping ⌘O free); agent recommendation accepted for the rest (⇧⌘I, as in Photos' Import).
