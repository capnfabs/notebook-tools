# Photo shapes named as people say them, by relink's own rule; photos at least 200px a side

The relink comparison table writes a photo's shape long side first, with its turn: `4:3, landscape`, `4:3, portrait`, `1:1, square`. The named ratios are 1:1, 5:4, 4:3, 7:5, 3:2, 16:10, 16:9 and 2:1, and any other ratio is written long ÷ short to two places, `1.43:1`. A size gets a name when it's the same shape as that ratio by the very test relink uses to accept a resized photo (`notebook_core::relink::same_shape`, each side within a pixel), so a name and a relink can't disagree. In the table, a file relink would accept shows the page's shape in both columns, so a resize never reads as another shape. A file it refuses never reads the same as the page: when both would (both within a pixel of 4:3 but two pixels apart, or the same to two places), both are written in decimals, with places added until they differ.

A photo under 200 pixels on its short side can't be added or relinked (`photo_meta::MIN_SIDE`, checked from the header in `photo_meta::read`). At that size there's nothing for Claude to read, and the pixel of rounding relink allows is too big a share of a side: a 3×3 file counted as a resized 4032×3024. Pages saved before this rule are left alone, and tests (`crates/core/tests/tiny_photos.rs`) show that a 1×1 page still loads, sends and exports without panicking. It feels important that small photos shouldn't cause anything to crash because of rescaling etc (we had a crash due to transforms dividing by zero at some point and so I'm extra cautious about it).

Reason: Human Taste (the format, the ratios named, sharing relink's rule, the 200px minimum refused as an error); unquestioned agent recommendation (the column rules and the decimal fallback).
